# 最小分工与交接

## 一条流程

用户提出需求 → 大模型告诉小模型怎么做 → 小模型返回产物 → 大模型判断 → 用户得到简短结论或必要选项。

不要把这条流程拆成多个会独立规划的 agent。大模型前后承担决策和判断，小模型只做内容生成与修改。

## 大模型交给小模型

只传当前工作需要的信息：目标文件或内容、具体操作、字段和名字、必要原文、需要保留的行为。现有内容能引用就引用，不要求大模型再写一遍完整实现。

指令形式先保持简单：短自然语言，或少量固定字段。不要为了形式统一而引入庞大协议、词表或中间语言。

## 小模型交给大模型

返回代码正文、局部修改或需要的 JSON/XML 内容。默认一个明确结果，不附分析、解释、方案比较或自行决定的下一步。

如果没有产出完整结果，就如实返回未完成状态，由大模型决定下一条指令；不让小模型自己启动反复尝试和学习。

## 大模型交给用户

给结论、必要差异和建议。需要用户取舍时，给少量明确选项及各自影响；没有取舍时直接说明结果，不制造额外问题。

这一步的目标是让用户快速判断，而不是再次展开一篇技术报告。大模型实际判断需要的工作仍要完成，但不必把长思考过程输出给用户。

## 适配器

适配器把结果对应到目标文件，生成文件名和展示外壳，呈现修改，并在大模型确认后执行已确认的内容。用户已有授权和确实需要用户选择的事项按当前任务处理，不额外设计多级审批平台。

第一版先完成一个指令、一个结果。以后如果多个文件能独立处理，再并行交给同一类小模型，不先建设依赖图调度系统。
