# 参考融合与当前收敛方案

**最终主线：大模型短指令 → 小模型快产出 → 大模型快判断 → 用户易决定。**

本版以用户最新简化要求为准。原来提出的错误学习、失败回收训练、复杂评测平台和编排路线不再属于方案。下面保留参考价值，不把参考的全部机制变成本项目需求。

## 发散之后，保留三个方向

**直接生成。** 大模型给出做法、字段和名字，小模型写结果。适合新增局部代码或结构化内容。

**直接修改。** 大模型给原文和明确改法，小模型只返回修改结果。这最符合“怎么做、怎么改”，建议优先挑这种真实任务试用。

**更快的输出。** 先用现有小模型、量化和常驻运行；如果需要统一指令习惯，可以做普通 SFT。扩散留作以后替换生成后端的参考。

已有模板可以直接用，但不以建设模板库、编译器或检索平台为当前目标。多文件可以以后同时生成，但不先做复杂调度。

## 当前推荐

首个尝试用一个常驻小代码模型，接收大模型的短指令和必要原文。小模型只给一个产物，大模型把它检查并收敛成用户需要的结论。适配器处理固定展示和确认后的写入。

普通 SFT 如需使用，只学习正常“指令 → 正确结果”的对应关系和输出习惯。不做错误学习，不收集线上失败来反复训练，不用强化学习。

## 最少的话，应该省在哪里

- 大模型给小模型：只说本次要做和要改的内容，复用已有上下文。
- 小模型给大模型：只回正文或修改结果，不回长解释。
- 大模型给用户：只给结论、关键变化和真正需要决定的事项。

不把简单任务拆成多个候选、多轮评审和自动修复流程。内容不合适时，大模型直接换一条明确指令，不额外建设学习系统。

## 为什么值得先这样试

它直接利用现有模型能力，额外组件少，容易看出是否节省时间。先观察真实任务是否按指令完成、结果是否可用、用户是否更快作出决定；与大模型直接完成同样任务做简单比较即可。

“不承担业务决策”不等于模型在技术上没有代码能力；本方案只是不要求小模型自己分析需求。实际速度和质量需要使用结果证明，不能因流程短就承诺必然更快。
