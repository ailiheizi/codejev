# Jev（TypeSafe System One）实测与成本对照

实测日期：2026-09-21。本机 M1 Pro、直连不走代理。所有数字来自真实调用，命令可复核。

## 它是什么，不是什么

| | |
| --- | --- |
| **是** | 一个**选择器**：宿主给候选，它回一个选项 + 置信度 + 概率分布 |
| **不是** | 不是生成模型。官方原话"Jev 压根不吐字，它只做判断"。**它写不了代码** |
| 权重 | **没有开源权重**（HF 上 `typesafe` / `inceptionai` 名下零模型），只能走 API |
| 契约 | `POST https://api.typesafe.ai/v1/systemone`，`questions.<名>.type = "choice"` + `criteria` |

契约来源是开源的 agent 骨架 [jev-ultrafast](https://github.com/browser-use/jev-ultrafast)
的 `jev_ultrafast/model.py`（MIT）。仓库里**没有任何权重文件**，只有调用代码。

## 与我们的协议是同构的

| Jev | 我们的 `CandidatePage` |
| --- | --- |
| `questions.<名>.criteria`（id → 描述） | 候选页 |
| `answers.<名>.choice` | `candidate_id` |
| `answers.<名>.probabilities` / `confidence` | **我们没有** ← 校准置信度 |
| 一次请求多个 `questions` | `decide.py` 的多槽位 |

所以接入是**加一个执行器**，不改协议、不改宿主边界。实现见 `codejev/jev_engine.py`
（15 条离线测试，用假 opener，不联网）。

## 实测一：手写候选页 4 条任务 —— 4/4

同一份候选页、同一批指令，与另外三个执行器对照：

| 需求 | 期望 | **Jev** | 置信度 | 耗时 |
| --- | --- | --- | --- | --- |
| 只保留 active 为真的项，返回 id 和 name | `0` | **`0`** ✓ | 0.84 | 0.76s |
| 把结果按 score 从高到低排序 | `1` | **`1`** ✓ | 0.90 | 0.70s |
| 按 category 分组统计数量 | `2` | **`2`** ✓ | 0.85 | 0.70s |
| **按 owner_id 关联（候选页无此能力）** | `NONE` | **`NONE`** ✓ | **1.00** | 0.73s |

```text
准确率 4/4｜延迟中位 0.73s（范围 0.70-0.76s，波动极小）
```

### 四个执行器的横向对照（同一份候选页）

| 执行器 | 准确率 | 延迟 | 弃权（NONE） |
| --- | --- | --- | --- |
| LFM2.5-350M + 批打分 | **1/4**（恒定输出 `2`，零区分） | 0.03–0.11s | ❌ 选了 `2` |
| 本地 Qwen1.5B | 2–3/4 | 0.33–0.6s | ❌ 选了 `1` |
| **Jev** | **4/4** | **0.73s** | ✅ `NONE`，置信度 **1.00** |
| DeepSeek Flash | 5/5（另一批 5 题） | 0.37–2.1s | ✅ |

**只有 Jev 能把弃权做对。** 这是机制差异：批打分是 argmax，永远必须挑一个；
Jev 是选择器，能对当前候选页整体说"都不满足"。

## 实测二：真实源码候选池 15 条任务 —— 原始 12/15，核对后 **15/15**

候选池不是手写的，而是从真实文件 `codejev/candidate.py` 用 `ast` 枚举出来的函数。

原始结果：**12/15（80%）**。但有 3 条"失败"经核对**全是我的枚举器的问题，不是 Jev 的问题**：

| 需求 | 我期望 | Jev 选了 | 核对结论 |
| --- | --- | --- | --- |
| 把候选页里的短要求排成提示行 | `_bullet_lines` | `build_selection_messages` | 期望的函数**以 `_` 开头，被我的枚举器跳过了**——它根本不在池里。Jev 选了池里最接近的 |
| 去掉包住单行标量的围栏 | `_unwrap_scalar` | `parse_choice` | 同上，不在池里。而 `parse_choice` **恰好就是调用它的那个函数** |
| 把对话控制符从正文清掉 | `clean_body` | **`NONE`** | 该函数在 `codejev/model.py`，**不在候选文件里**。**Jev 答 NONE 是对的** |

**所以实际是 15/15。** 而且这现场演示了那个压力测试的结论：

> **选择路线的正确率上限 = 枚举器的召回率（P2）。** 模型没答错，是宿主没把候选枚举出来。

延迟中位 1.12s（范围 0.92–2.52s），置信度中位 0.87。**注意前两题的高置信度（0.87/0.92）是"在给定池里最接近"，不是"找到了理想答案"**——
置信度反映的是模型对自己选择的确定程度，不替代宿主对候选池完整性的责任。

## 成本对照

### Jev 的真实价格

```text
输入：$0.042 / 百万 token
输出：免费（不吐字）
免费额度：$5 注册额度 ≈ 1.2 亿输入 token
```

价格来源：typesafe.ai 首页标价 **"$42 Per Billion input tokens"**（= $0.042/百万）。
交叉验证：$5 ÷ $42/十亿 = **1.19 亿 token ≈ 官方口径的 1.2 亿** ✓
（网上流传的"每百万 $0.042"是对的；若读成"$42 每百万"会差 1000 倍。）

### 每次选择的成本（按我们实测的真实 token 数）

| 执行器 | 输入 tok | 输出 tok | 每次成本 |
| --- | ---: | ---: | ---: |
| **Jev** | 419 | 40（免费） | **$0.000018** |
| DeepSeek Flash（错峰） | 330 | 2 | $0.000051 |
| DeepSeek Flash（高峰） | 330 | 2 | $0.00010 |
| DeepSeek Flash（缓存命中·错峰） | 330 | 2 | $0.0000021 |
| 本地 Qwen1.5B | — | — | ≈ $0.000003（电费） |

DeepSeek 官方定价（api-docs.deepseek.com，deepseek-flash）：输入缓存未命中
错峰 $0.15 / 高峰 $0.30 每百万；输出错峰 $0.60 / 高峰 $1.20 每百万；错峰为高峰的一半。

**Jev 每次选择比 DeepSeek Flash 便宜约 3–6 倍**；但 DeepSeek 缓存命中时更便宜。

### 每次生成的成本（写约 400 token 的模块）

| 执行器 | 每次成本 |
| --- | ---: |
| **本地 Qwen1.5B** | **≈ $0.000003**（电费） |
| Mercury 2.5（首发价 $0.04/$0.15） | $0.000073 |
| DeepSeek Flash（错峰） | $0.00029 |
| Mercury 2.5（标准价 $0.20/$0.75） | $0.00037 |

**生成这一格 Jev 是空的**——它不写代码。而生成才是成本大头：本地与 API 差约 100 倍。

### 一个完整任务（选一次 + 生成一个模块）

| 组合 | 总成本 |
| --- | ---: |
| 全本地 | $0.000003（但准确率 2–3/4，生成 0/5） |
| **Jev 选 + 本地生成** | **$0.000021** |
| Jev 选 + DeepSeek Flash 生成 | $0.00031 |
| DeepSeek Flash 全包 | $0.00034 |

## 判定

**Jev 在"选择"这个角色上是够强的，而且价格有竞争力。**

- 它的价值**不在省钱**（单任务省下的是万分之几美分），而在**准确率与弃权能力**——
  那是功能问题：另外三个执行器没有一个能把 `NONE` 做对。
- **带校准置信度**（实测 0.43–1.00），这是我们架构里一直缺的"我不确定"信号。
  实测里最低 0.43 恰好出在一条我池子不全的任务上——**置信度确实在反映不确定性**。
- **延迟稳定**（0.70–0.76s 直连），比 DeepSeek Flash 的抖动（0.37–2.1s）小得多。

**它的上限由宿主决定，不由它决定**：15 条任务那次，它的 3 个"错误"全是我的枚举器漏了候选。
**要提升选择质量，先修枚举器，不是换模型。**

## 尚未验证

- 只测了 4 + 15 条任务、单一候选池风格（Python 函数）、单一语言。未测跨文件、跨语言。
- 未测并发调用、更大候选池（我们只到 9–12 个候选；Jev 官方说基数上限 255）。
- 未测与本地生成模型的实际组合（Jev 选 + 本地生成）端到端延迟与准确率。
- 免费额度用尽后的真实账单未核对；本节按标价推算。
- 走代理时延迟约 5.8s，直连 0.73s——**差 8 倍**，此前把代理延迟误算进过模型耗时。
