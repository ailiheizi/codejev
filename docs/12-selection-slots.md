# 选择路线的槽位：怎么把更多任务从"生成"挪到"选择"

实测已经说明问题：同一个模型、同一份源码，**选择路线 5/5，生成路线 0/5**。
所以让项目变强的方向不是换模型，而是**让更多任务能用选择表达**。

本文把这件事说具体。

## 一个任务 = 若干个"槽位"上的决策

选择路线的形状是：**宿主提取候选 → 模型只在候选里选 → 宿主确定性组装**。
模型能选的东西，就是一个**槽位**。每个槽位有三件东西：

| | 说明 | 现在是谁在做 |
| --- | --- | --- |
| **候选从哪来** | 从源码里确定性提取，模型只能引用候选 id | `extract()` |
| **怎么渲染** | 宿主把选中的 id 变成代码，逐字节保留其余部分 | `assemble()`（libcst） |
| **模型要回什么** | 只回 id，不回代码 | `Decision` |

**槽位越多，能用选择表达的任务越多，落到生成路线的任务越少。**

## 现在已经落地的槽位（3 个）

```python
Decision(function_id, filter_field, return_fields, sort_field=None, sort_desc=False)
```

| 槽位 | 状态 | 谁决定它可用 |
| --- | --- | --- |
| `filter_field`：按哪个字段做真值过滤（或不过滤） | 已上线 | 始终可用 |
| `return_fields`：返回哪些字段、什么顺序 | 已上线 | 始终可用 |
| `sort_field` / `sort_desc`：按哪个字段、升序还是降序 | **已上线，默认关闭** | 调用方必须显式传 `sort_enabled=True` |

能表达的任务因此分两类：**"过滤列表函数 + 裁返回字段"** 用两个基础槽位就够；
**"按金额排序""按名字排序"** 需要排序槽位，且必须由调用方先启用。

"只要大于 100 的""去重""只取前 10 条"仍然落在生成路线那边——而那条路线实测 0/5。
它们对应下面的比较、去重、限量槽位。

### 排序槽位：一次真实回归，和挡住它的闸门

排序槽位刚加进去时出过回归：提示词的示例里出现 `s=f1,d=desc` 之后，
**用户没有要求排序的 5 条指令全部被模型错误地加上排序。**

修法不是改措辞，而是把启用权从模型手里拿走：

```text
大模型计划未启用 sort
→ 宿主不传 sort_enabled：提示词和用户消息都明确禁止 s / d
→ 小模型即使回了合法的 s / d 也被拒绝
```

`sort_enabled` 是调用方（大模型计划）传下来的协议位，**不从 instruction 里猜**。
所以"让模型自己判断该不该排序"这条路已经被排除，不是靠模型守规矩。

### 排序槽位的四项数字（已量，2026-09-20）

`bench/sort_slot.py` 就是为这四件事写的，数字已记进[实测结果](11-measured-results.md)的
「排序槽位的四项实测，以及它顺手暴露的一次生产回归」一节：

| 要量什么 | 结果 |
| --- | --- |
| 模型选得对吗 | 排序任务 **18/18**（6 类任务 × 3 次，运行时行为判定） |
| 输出多了几个 token | 用上槽位 **+15 tokens**；不用槽位的决策 **+0** |
| 老任务有没有被拖累 | 4 条不排序对照 + 老任务 A 全部 **3/3**（15/15） |
| 拒绝得清不清楚 | **8/8**，每条报的都是各自真实原因（不是笼统的那道闸） |

**但这次补测顺手挖出一个更严重的问题，而且已经修掉了**：加排序槽位时生产提示被改了，
删掉了那行 `正确形状示例`，1.5B 随即开始**整个省掉 `f` 键**（回 `{"r": ["f1","f2"]}`）。
宿主把"键缺失"当"不过滤"——这是合理设计，但它让这次失败**不会报错**：
过滤条件那行代码被删掉，产物仍是合法 Python。当时不排序的老任务从 3/3 掉到 0/3，
生产 CLI 上 `--dry-run` 就能复现。定位与修法的完整证据见实测结果那一节。

教训直接并入下面的规矩：**"老任务有没有被拖累"不是走过场，它真的会抓到东西。**

## 候选槽位（按价值排序）

| 槽位 | 状态 | 解锁的指令 | 候选来源 | 渲染成什么 |
| --- | --- | --- | --- | --- |
| **排序** | **已上线（默认关闭），四项数字已量** | 按金额从高到低 / 按名字排序 | 同字段候选 | `rows.sort(key=..., reverse=...)` |
| **比较** | 未做 | 只保留 total 大于 100 的 / 状态等于 active 的 | 字段 + 运算符 + 字面量 | `if x > 100:` |
| **去重** | 未做 | 按 id 去重 | 字段候选 | 已见集合 |
| **限量** | 未做 | 只返回前 10 条 | 数字（小枚举或自由值） | `rows = rows[:10]` |

排序排第一，理由是它最常和"过滤 + 裁字段"一起出现——**我们自己的基准函数里就有 `rows.sort(...)`**。
它已经加进去并量完了：原有排序会被按决策改写，而不是像以前那样只能原样保留。
下一个要加的是**比较**（"只保留 total 大于 100 的"这类指令目前无槽位可用）；
但按下面的规矩，必须先有真实任务和四个数字，才轮到它。

## 加槽位的代价，必须按这个规则加

**每加一个槽位，决策的输出就可能变长。** 而输出 token 是慢的那部分（实测解码占 51%）。
但"所有决策都变长"这句话**实测不成立**——排序槽位的量法是这样的：

- 不用槽位的决策：**+0 tokens**（启用条款根本没进提示，输入侧只多约 20 个 prefill token）
- 用上槽位的决策：**+15 tokens**（28 → 43）

关键在实现方式：**把启用条款做成只在启用时才拼进提示**，而不是常驻在提示里。
这样"加槽位"就只对用得起它的任务收费：

- **收益**：某一类任务从"生成路线 0/5"变成"选择路线 5/5"，且不用重写整个函数
- **代价**：只有真正用上这个槽位的决策多几个 token（+15）

所以规则是：**只为高频任务类型加槽位**，而且每个都要先量出来再决定要不要留，
并且**必须按上面的方式做成 opt-in**，否则真会变成对所有决策都收税。
这不建 DSL、不建模板库——**是一个一个加，每个都有真实任务和实测数字支撑。**

## 每加一个槽位要量什么

1. **模型选得对吗**：同一类任务的正确率（用运行时行为判，`exec` 后真调用，不靠看）
2. **输出多了几个 token、慢了多少**
3. **老任务有没有被拖累**：只用旧槽位的任务，正确率和耗时是否不变。
   必须用**配对照组**（同一份源码、同一条指令、只差"要不要排序"），只看槽位任务过没过抓不到东西——
   排序槽位就是这么抓到那次"过滤条件被静默删掉"的回归的
4. **拒绝得清不清楚**：候选里没有合适项时，是否明确报错而不是猜一个。
   注意别被"闸门先拒了"骗成通过：拒绝原因必须是**这个槽位自己的校验器**报出来的

## 这件事的上限在哪

Loom 的实测给了一个参照：他们的"候选池密度"实验显示，**灌密候选池之后才收敛**——
说明这类系统的上限在**候选质量**，不在模型能力。

对我们的含义很直接：**选择路线的上限由 `extract()` 决定，不由小模型决定。**
提取做得越全，能进 5/5 路线的任务就越多。

## 现在不做的事

- 不做通用 DSL、不做模板库、不做检索平台（文档里已列禁止项）
- 不做自动修复闭环：某个槽位不合适，由大模型重新下指令，不由程序自动重试
- 不为了"覆盖更多情况"而加槽位——**没有真实任务支撑的槽位不加**
- 加槽位必须做成 opt-in（启用条款只在启用时进提示），否则会变成对所有决策收税
- 加完必须把那个槽位的四个数字量出来并记档，**"老任务有没有被拖累"要用配对照组量**
