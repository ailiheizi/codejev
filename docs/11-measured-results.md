## 任务 A：简单改动（两条路线都做得到）

源码函数返回全部字段、完全不过滤；指令是"只保留 active 为真的项，返回 id 和 name，
保持原顺序"。8 次独立试验，每次都用运行时真实调用判断对错（不是看代码像不像）。

| 路线 | 通过 | 平均生成耗时 | 输出长度 |
| --- | --- | --- | --- |
| 生成（小模型写正文） | 8/8 | 0.92 s | 70 tokens |
| 选择（宿主提取＋小模型只选＋宿主组装） | 8/8 | 0.60 s | 36 tokens |

结论：这个难度下两条路线都可靠；选择路线输出少一半，生成耗时约为生成路线的三分之二。

## 任务 B：真实形状的函数（差距出现在这里）

源码带**前置守卫**、**复合条件**和**循环后排序**：

```python
def paid_orders(orders):
    """返回已付款订单的编号与金额，按金额从高到低。"""
    if not orders:
        return []
    rows = []
    for order in orders:
        if order.paid and not order.shipped:
            rows.append({"order_id": order.order_id, "total": order.total})
    rows.sort(key=lambda r: -r["total"])
    return rows
```

指令：只保留 paid 为真的项，返回 order_id 和 total，其他不变。5 次独立试验。

| 路线 | 通过 | 实际表现 |
| --- | --- | --- |
| 生成 | **0/5** | 每次都把原文件**原样吐回**，`paid and not shipped` 复合条件一个字没改 |
| 选择 | **5/5** | 正确改成只看 `paid`；输出 36 tokens |

选择路线在这个函数上同时满足了三件事：按新条件过滤、空输入仍然走 `if not orders: return []`
返回 `[]`、循环后的 `rows.sort(...)` 仍然执行（结果确实按 total 降序）。后两件正是
"其他不变"的含义，而生成路线连第一件都没做到。

**注意**：生成路线的 0/5 不是语法错误，产物是合法且能跑的 Python——它只是没有执行指令。
这类失败在只看 diff 时很容易被放过，因为它看起来像一个"没改动的干净文件"。

## 实测中发现并修掉的缺陷

这些是靠真跑暴露出来的，不是读代码想出来的：

1. **提示词把占位符当成了取值**：决策提示里写了 `"filter_field": "c0 或 null"`，
   小模型逐字照抄，导致每一次决策都被判为非法 id。改成描述形状并给一个真实示例。
2. **"加一个过滤条件"这条最常见的指令无法表达**：候选提取只把*原文已经用来判断*的字段
   当成条件候选，而原文根本没有判断可抄。改成所有观察到的名字都可作为条件候选，
   已在判断里出现过的排在前面。
3. **小模型把 `null` 写成字符串 `"null"`**：这是 JSON 写法差异，不是新 id，
   按"不过滤"处理；其余任何字符串仍然必须匹配真实候选 id。
4. **组装会静默删代码**（最严重）：早期版本把函数体拆成"docstring＋累加列表＋for 循环＋
   return"重新拼接，于是前置守卫和循环后的 `sort` 被悄悄丢掉——diff 看起来很干净，
   实际删掉了正在工作的代码。现在改用 libcst 只改两处（过滤条件、append 的字典），
   其余逐字节不动；无法安全处理的形状直接拒绝，绝不猜。
5. **对照脚本被一次坏输出打断**：模型返回非字典列表时 `.get()` 抛异常，整轮对照崩掉，
   而不是把这一次记成失败。已改为先判类型再做取值比较。

## 已知边界（尚未解决）

- **选择路线一次只能表达一个条件**。原文是 `paid and not shipped` 这种复合条件时，
  重写后会变成只看 `paid`，范围与原来不同。程序会附一条提示交大模型判断，
  但**不会**自动改用别的路线，也不会猜用户想要哪个。
- **选择路线只支持"循环里往累加列表 append 字典"这一种函数形状**，其他形状抛
  `DecisionError` 拒绝；这是有意的，宁可说做不了，也不能改错。
- 两条路线都只处理**单个函数**；多文件、shell 执行按文档要求未实现。
- **没有做 SFT、扩散或错误学习**，本轮全部使用现成模型；文档里这些仍是可选项。
- 上述耗时是**单机小样本**（5–8 次），不是通用性能结论。选择路线的耗时优势在任务 A
  最明显；任务 B 里两条路线的生成耗时接近（0.8–1.3 s），差别主要出在**正确率**上。

## 附加实验：换更小的模型（0.5B）是不是更快的杠杆

本节只追加，不改上文任何数字。实测日期 2026-09-19，同一台机器、同一时段。
脚本 `bench/speed.py`，四个变体、同一份源码、同一条指令、温度 0；每个变体在模型
常驻后跑两次独立的 5 次（各 5 次）。正确率一律用**运行时行为**判断：真的 `exec`
产物、真的调用函数，检查过滤结果、返回字段是否恰好等于要求、空输入是否仍走守卫
返回 `[]`、循环后的 `sort` 是否仍让结果按 total 降序。输出变快但改错的一律记失败。

任务 A 就是 `bench/compare.py` 的固定任务（源码与常量直接 `import` 复用，那边一个字
未改，判断口径也一致）；任务 B 用带前置守卫和循环后排序的 `paid_orders`。
（守卫子句在运行时对空输入不可分辨——有没有它，空输入都返回 `[]`——所以除空输入
行为检查外，另加一条确定性的 AST 形状检查；sort 由"结果必须严格降序"的运行时样本
分辨，该样本特意让过滤后的剩余项按输入顺序是升序。）

### 0.5B 的实际失败：它没有在选择，它在照抄示例

任务 A 的 select 上，0.5B 两次运行共 10 次全部失败，每次都是同一句
（温度 0，输出完全确定，两次运行逐字相同）：

```
{"function": "fn0", "filter_field": "c0", "return_fields": ["f2", "f3"]}
→ 决策不合法: 未知的字段 id：'f3'（可用：f0, f1, f2）
```

任务 A 的候选表是 `f0=id, f1=name, f2=active`，条件 `c0=id, c1=name, c2=active`，
正确答案是 `c2` ＋ `["f0","f1"]`。0.5B 的 `return_fields` 恰好是**系统提示示例里原样
写着的** `["f2", "f3"]`（示例全文为
`{"function": "fn0", "filter_field": "c1", "return_fields": ["f2", "f3"]}`），
条件 id 则停在候选表里的第一个条件 `c0=id`，完全没有按照指令去找 `active`。

任务 B 的 candidates 恰好是 `f2=order_id, f3=total, c0=paid`，与示例 id 撞上了，
于是 0.5B 那句同样的输出在任务 B 上变成了正确答案——**任务 B 的 5/5 是巧合，
不能当作它会做决策的证据**。

诊断（`--diagnostic`，不属于四个变体）：把系统提示里那行示例删掉，其余一字不改，
在任务 A 上再跑 5 次：

- 0.5B：5/5 次输出 ```json [{"id": "1", "name": "Alice"}, …] ```（一个 JSON 数组，
  不是决策对象），解析全部失败——它连输出形状都是靠示例撑起来的；
- 1.5B：5/5 次输出合法对象，但 `return_fields` 变成 `["f0","f1","f2"]`（多选了一个
  字段），也变差了。

任务 A 的 generate 路线上，0.5B 10 次全部多留了 `active` 字段
（`['active', 'id', 'name']`，要求是 `['id', 'name']`），即"裁字段"这一半也没做到。

### 为什么换小只有约 2 倍：固定成本实测

（提示长度为任务 A 的 select 提示：system 提示＋候选表＋指令。）

| 模型 | 决策提示 tokens（任务 A select） | 只生成 1 个 token 的耗时（prefill＋单次调用固定成本） |
| --- | --- | --- |
| 1.5B | 211 | 0.32–0.34 s |
| 0.5B | 211 | 0.17–0.18 s |

把 system 提示从 226 字符压到 6 字符（提示 211→111 tokens）：1.5B 0.34→0.25 s，
0.5B 0.18→0.16 s。

于是 1.5B 的一次 select 决策（0.69 s）里，约 0.34 s 是固定前缀的 prefill，
约 0.35 s 才是解码那 36 个 token（解码本身约 103 tok/s，上表的 52 tok/s 是把 prefill
摊进去的有效值）。换到 0.5B：固定成本约减半（0.34→0.17 s），解码部分也因为每个
token 更快、输出更短而大约减半（约 0.35→0.16 s），所以总量只快 1.7–2.3 倍
（同一次运行内比较），而不是参数量暗示的 3 倍。

### 结论

在本机这个任务上，**把模型换小不是正确的速度杠杆**：0.5B 的 select 稳态单次
0.29–0.53 s，确实比 1.5B 的 0.65–0.98 s 快约 2 倍，但代价是在简单任务（任务 A）上
0/10 全错——它照抄系统提示示例里的 return_fields、条件则停在第一个候选，而不是按
指令在候选表里做选择，任务 B 的 5/5
只是那些 id 恰好撞对了；generate 路线同样 0/10。省下的 0.35–0.45 s 换来的是完全不可用
的产物，而且这条路线靠宿主校验挡住了错误（`未知的字段 id：'f3'` 被 `parse_decision`
拒绝），换小模型只会把失败搬到更晚、更难解释的地方。同样的时间预算更值得花在
**提示与调用结构**上：固定前缀的 prefill 实测就占 1.5B 决策耗时的近一半（0.32–0.34 s，
其中 system 提示约占 0.09 s），让这段固定前缀的 KV cache 复用、或缩短 system 提示，
是不牺牲正确率的杠杆（前者涉及 `chooseonly/model.py`，本轮未实现、未实测）。
以上都是**单机小样本**（每变体两次各 5 次）观测，机器当时有其他负载（load average 8–19，
10 核），两次运行的均值最大差到 2 倍以上（1.5B＋select 任务 B：1.53 s 与 0.72 s），
不构成通用性能结论；通过/失败模式在五次完整运行中完全一致，时间只报区间。
之后又跑了一次确认（负载更重），**通过/失败模式仍逐字相同**，但绝对耗时最高涨到
前两次的 3 倍左右（0.5B＋generate 任务 A：0.58 s → 1.70 s），所以时间数字只能在同一次
运行内相互比较，不能跨运行比较。

## 选择路线的延迟拆解与更短输出探针

用 `mlx-lm` 的 `stream_generate` 逐 token 收时间戳，把一次选择路线调用拆成四段；模型加载
与两次预热不计入。模型 1.5B 4bit、温度 0、提示 211 token、输出 39 token，9 次同一请求
（`bench/timing.py`，机器当时有其他负载，load average 6–12）：

| 段 | 均值 | 最小 | 最大 | 占比 |
| --- | --- | --- | --- | --- |
| 前置开销（detokenizer 构造等调用前准备） | 0.094 s | 0.090 s | 0.100 s | 14% |
| 提示处理（首 token 时间） | 0.220 s | 0.214 s | 0.229 s | 33% |
| 解码（首 token 之后的 38 步，9.12 ms/token） | 0.347 s | 0.333 s | 0.371 s | 51% |
| 收尾（同步、wired limit 复原） | 0.014 s | 0.013 s | 0.015 s | 2% |
| 合计墙钟 | 0.674 s | 0.662 s | 0.693 s | 100% |

同夜另外三次运行的墙钟均值 0.646–0.708 s（后台负载越高越慢；最小值 0.598 s，与上面的
0.60 s 基线一致）；非流式对照 0.542–0.675 s，与流式口径接近，说明这四段就是这条路径的
真实预算。模型加载本次 0.39 s，早几次 0.94–1.12 s（取决于页缓存）。

**解码占一半，提示占三分之一。** 提示处理约 960 tok/s，解码约 110 tok/s，所以 211 个输入
token（0.22 s）反而比 39 个输出 token（0.35 s）便宜。除解码外的三段共 0.33 s 与输出长度
无关，是缩短输出突不破的底。

顺带量到一件与模型无关的事：`mlx-lm` 0.31.3 的 `stream_generate` 每次调用都执行
`tokenizer.detokenizer`，而该属性是 `return self._detokenizer_class(self)`——每次都新建一个
BPE 流式 detokenizer（遍历 15 万条词表），不缓存；直接量它是 0.085–0.099 s/次。同一请求
改用 `generate_step` 直驱、只在最后 decode 一次：0.546 s → 0.447 s（各 9 次均值），省
0.099 s，与单独量的构造成本一致。

### 更短的输出值多少

同一决策、同一候选表、同一任务文本，只改系统提示里的输出契约，每种 9 次轮转执行（后台
负载漂移摊到每种格式上）；文本先经 `clean_body` 去控制符，与生产路径一致：

| 格式 | 解析通过 | 输出 token | 解码均值 | 墙钟均值 | 墙钟最小 |
| --- | --- | --- | --- | --- | --- |
| JSON（现状）：`{"function":"fn0","filter_field":"c2","return_fields":["f0","f1"]}` | 9/9 | 39 | 0.332 s | 0.662 s | 0.548 s |
| 精简 JSON：`{"f":"c2","r":["f0","f1"]}` | 9/9 | 29 | 0.246 s | 0.556 s（−18%） | 0.477 s |
| 裸 token：`c2 f0 f1`（第一版措辞） | **0/9** | 14 | 0.109 s | 0.428 s | 0.368 s |
| 裸 token（改过措辞） | 9/9 | 9 | 0.070 s | 0.439 s（−35%） | 0.327 s |

温度 0 下每种格式的 9 次输出逐字相同，所以“解析通过率”是对一种措辞的确定性判断，不是
9 个独立样本。裸 token 的成败与措辞强相关，三种合理写法给出三种结果：写“形状是
〈条件 id〉〈字段 id〉…，示例 c2 f0 f1”时模型回 `fn0=f0,f1,name,f2=active`，把候选表抄了
回来；把示例写成条件句“如果条件是 c2、要返回 f0 和 f1，你只回：…”时多回一个函数 id
（`fn0 c2 f0 f1`）；明确禁掉字段名、等号、引号、括号，示例写成短标签“正确的回复示例：
c2 f0 f1”才逐字回 `c2 f0 f1`。

**结论：缩短输出是真杠杆，但幅度有限，且要付可靠性代价。** 精简 JSON 稳拿 18%
（0.66→0.56 s），不必动措辞；裸 token 能到 35%（最小 0.33 s，已贴到前置＋提示＋收尾的
底），但它对措辞敏感——1.5B 上三种写法只有一种被逐字执行——而且只验了一条指令、一张
候选表，换任务是否仍可靠没有验证。按本次数字，最稳的一刀反而是那 0.099 s 的
detokenizer：与模型、提示、输出长度都无关。另：换更小的模型会同时压提示与解码两段
（两段都是访存瓶颈），与缩短输出不冲突；但前置＋收尾那 0.11 s 任何模型都省不掉。

以上是**单机小样本**（一条指令、每种 9 次、M1 Pro 16 GB），机器当时有其他负载，不是通用
性能结论。

## 扩散语言模型在本机的实测（2026-09-19，M1 Pro 16 GB）

问题：扩散语言模型每次前向能并行产出多个 token（社区指标 TPF），
理论上需要的串行步数远少于自回归，那么它在本机能不能替代现在的小模型。
结论先说：**能在本机跑，质量也够用，但比现有自回归基线慢 2.7–3.7 倍。**

### 先查环境：mlx-lm 跑不了任何扩散架构

`mlx-lm` 0.31.3 只按 `config["model_type"]` 去 `mlx_lm.models.<type>` 找实现。
`models/` 下 120 个架构文件里没有任何 diffusion / llada / mdlm 文件，
`MODEL_REMAPPING` 里也没有相关条目。直接调它的分派函数：

```
llada       -> ValueError: Model type llada not supported.
llada2_moe  -> ValueError: Model type llada2_moe not supported.
a2d-qwen3   -> ValueError: Model type a2d-qwen3 not supported.
qwen2       -> OK（当前基线走的就是这条）
```

所以 `mlx-community/LLaDA-8B-Instruct-mlx-4bit` 的模型卡虽然写着"用 mlx-lm 加载"，
在本机这份 mlx-lm 上加载不了（该卡是 2025-03 用 mlx-lm 0.21.0 转的，属自动生成的模板文案）。
可行路径只有 `mlx-vlm`：0.7.1 里有 `models/llada2_moe/`、`models/nemotron_labs_diffusion/`
等专用扩散实现，还有独立的 `generate/diffusion.py` 去噪循环。

### 选了哪个模型，为什么

| 候选 | 实际体积 | 结论 |
| --- | --- | --- |
| mlx-community/LLaDA2.1-mini-4bit | 9.17 GB | 能跑（需 mlx-vlm），但 16 GB 机器同时有其他进程，**未下载未测** |
| mlx-community/LLaDA2.0-mini-preview-4bit | 9.17 GB | 同上 |
| mlx-community/LLaDA-8B-Instruct-mlx-4bit | 4.52 GB | mlx-lm 无对应架构，加载即失败 |
| dllm-hub/Qwen3-0.6B-diffusion-mdlm-v0.1 | 1.52 GB | 需要 torch + trust_remote_code，本机未装 torch，未测 |
| **mlx-community/Nemotron-Labs-Diffusion-3B-4bit** | **2.16 GB** | **本次实测对象**（mlx-vlm 0.7.1 原生支持，显存占用 2.36 GB） |

实测对象是 NVIDIA 的 Nemotron-Labs-Diffusion-3B（4 bit MLX 转换版），
权重从 ModelScope 拉取，落盘 2,155,620,090 字节，与仓库列出的 2155.62 MB 逐字节一致。
它同时支持自回归和扩散两种解码方式，**同一份权重只换注意力模式**，
因此可以把"扩散解码本身"和"换了个模型"两件事分开——这是本次最有信息量的一组对照。

### 同题同参对照（全部 5 次，温度 0，判断标准是 exec 产物后真的调用函数）

任务与基线完全一致：`bench/compare.py` 的 `BENCH_SOURCE`，
"只保留 active 为真的项、只返回 id 和 name、保持原顺序"。

| 后端 | 路线 | 通过 | 墙钟均值 | 输出 token | 前向次数 | TPF | 每次前向 | tok/s |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Qwen2.5-Coder-1.5B-4bit（现状） | 生成 | 5/5 | 1.23 s | 70 | 70\* | 1.00\* | 17.5 ms | 61.6 |
| Qwen2.5-Coder-1.5B-4bit（现状） | 选择 | 5/5 | 0.67 s | 36 | 36\* | 1.00\* | 18.1 ms | 55.3 |
| Nemotron-3B，**自回归模式** | 生成 | 5/5 | 2.96 s | 98 | 98\* | 1.00\* | 30.1 ms | 33.9 |
| Nemotron-3B，**自回归模式** | 选择 | 5/5 | 1.82 s | 28 | 28\* | 1.00\* | 64.6 ms | 15.5 |
| Nemotron-3B，**扩散模式** | 生成 | 5/5 | 4.53 s | 77 | **22** | **4.23** | 206 ms | 17.2 |
| Nemotron-3B，**扩散模式** | 选择 | 5/5 | 1.77 s | 28 | **8** | **3.88** | 219 ms | 16.0 |

\* 自回归每次前向必然只出 1 个 token，这是定义不是测量值；扩散那两列来自
`GenerationResult.diffusion_denoising_steps`（真实去噪前向数）和 `diffusion_work_tokens`（被接受的位置数）。

token 数按各自分词器统计，跨后端不可直接比；同一后端内部可比。
加载：基线 0.54 s，Nemotron（mlx-vlm）1.44–2.87 s；磁盘 2.16 GB，MLX 峰值显存 2.36 GB。

**质量上扩散模型完全够用**：两条路线各 5/5，输出 JSON 与函数正文都通过运行时行为检查，
没有出现基线在真实形状函数上那种"原样吐回"的失败。输出契约是守住的。

**速度上不要指望**。同一份权重换解码模式后：

- 生成路线：自回归 30.1 ms/token → 扩散 58.8 ms/token，**慢 1.95 倍**；
- 选择路线：自回归 64.6 ms/token → 扩散 62.5 ms/token，**持平**（差异在噪声内）；
- 前向次数确实大幅下降：生成 98 → 22（4.5 倍），选择 28 → 8（3.5 倍）。

也就是说，**前向次数省的，被"每次前向更贵"几乎原样吃掉了**。
扩散的每次前向要对整个块做双向注意力、不能复用 KV cache，单次成本是自回归的 3–7 倍。
对比现有基线，扩散模型生成慢 3.7 倍、选择慢 2.7 倍。

### 调参能不能救回来（生成路线，5 次）

| 配置 | 墙钟 | 前向 | TPF | 每次前向 |
| --- | --- | --- | --- | --- |
| 画布预算 1024（项目的现值） | 4.53 s | 22 | 4.23 | 206 ms |
| 画布预算 128 | 3.65 s | 22 | 4.23 | 166 ms |
| 画布 128 + `block_length=128` | 12.86 s | 29 | 4.38 | 443 ms |

但前向从 8 次降到 5 次、TPF 从 3.88 涨到 **12.6**、每次前向从 219 ms 涨到 363 ms。

**这一行是本次最值得记住的观察：TPF 涨了 3.2 倍，端到端时间一点没变。**
TPF 只是分子分母同时变化的比值，块越大并行度越高、但每次前向也越贵，
单看 TPF 会得出与用户实际等待时间相反的结论。

### 厂商数字 vs 本次实测（必须分开看）

- LLaDA2.1-mini 官方基准表写 TPF 5.34（S 模式）、2.0-mini 写 2.60；**本次没有测这个模型**。
- Nemotron-Labs-Diffusion 官方写"比 Qwen3-8B 高 5.9 倍 tokens/forward"，
  DGX Spark（8B、并发 1、w4a16）"112 tok/s，比自回归 41.8 tok/s 快 2.7 倍"。
- 本次实测：TPF 4.23 / 3.88，与厂商"每前向 token 数"的口径同一量级；
  但端到端 **17.2 tok/s**，比上面那个 DGX 数字低约 6.5 倍，且慢于本项目自己的自回归基线。
  厂商数字来自 NVIDIA 硬件 + 定制 CUDA kernel，本机是 M1 Pro + mlx-vlm 的 Metal 实现，
  两者不可互推。

### 判定

**（b）可用但不更快**——在本机、本任务上比现有自回归基线慢 2.7–3.7 倍，
且同一份权重下扩散解码本身不快于自回归解码。

不是"跑不起来"，也不是"质量不够"：质量 10/10 通过，TPF 也确实有 4 左右。
输在每次前向的成本：2.16 GB 权重 / 206 ms ≈ 10 GB/s，远低于 M1 Pro 约 200 GB/s 的带宽，
说明扩散这条实现路径是访存之外的瓶颈（无 KV 复用、逐块双向注意力、每步 Python/调度开销），
单次前向贵 3–7 倍，正好抵消并行度收益。

## 批处理 vs 顺序调用：N 份独立工作放进一次前向值多少（2026-09-19，M1 Pro 16 GB）

架构要把任务拆成 N 份**互相独立**的小工作分别问小模型。N 个并发**进程**已经确定不会带来
N 倍吞吐（一块 GPU），所以真正可能的杠杆是**批处理**：N 条序列拼进同一次前向。
本节实测这条路径，用 `bench/batching.py`（8 份不同的真实工作：不同源文件、不同函数、
不同字段；温度 0；两种路径共用同一份权重、同一批 token）。

**结论先说：批处理在本机只值 1.16–1.35 倍，不是 N 倍；N=4 约 1.15–1.2 倍，N=8 约 1.3–1.35 倍。**

### 口径与正确性前提

- 批量路径用 mlx_lm 的 `BatchKVCache`：提示**左填**（所有序列在同一个绝对下标结束，
  首 token 统一在 `width-1` 读出），解码阶段每条序列各喂自己的上一个 token。
  这条路径是本项目第一次引入，写法与理由写在 `bench/batching.py` 文件头。
- **mask 对不对是本次的前提**，所以每条答案都与顺序路径在温度 0 下逐字比对：
  两轮共 **93/93 逐字一致**（第一轮 3 轮 45 条：3/3、6/6、12/12、24/24；
  第二轮 4 轮 48 条：16/16、32/32），输出 token 数也 93/93 一致。
  不一致会逐条打印，本轮没有触发。
- 另用**不同长度**的合成提示（37/53/71 token，填充最多 34 个 token）单独验过左填 mask：
  批处理与顺序逐 token 一致（主实验 8 条提示都是 193–215 token，填充最多 22 个，压不满 mask）。
- 正确性不是"看代码像不像"：解析决策 → `chooseonly.decide.assemble` 组装 → 真的 `exec`、
  真的调用函数，核对过滤结果与返回字段（空输入还要仍返回 `[]`）；
  `active_users` 这一条同时过一遍 `bench/compare.py` 的 `check_runtime_behaviour`。
- 跑之前修过第一版 4 处（它没被跑过）：解码步多传了一根轴（必崩）、
  正确性检查拿模型回的决策 JSON 当函数体直接 `exec`（会把每条都判成失败）、
  共享前缀的计时把前缀 prefill 重复计了 3 次、输出头对 `tie_word_embeddings=true`
  的模型走了全量 logits 兜底（改成 `embed_tokens.as_linear` 只算末位）。

| 8 | 1.723 GB | 1.723 | 1.723 |

本进程最大 RSS 1162–1168 MB。权重本身约 0.87 GB，批到 8 时 MLX 峰值只多 ~0.5 GB，
16 GB 机器够用。

### 判定

1. **批处理是真实可用的机制，但本机收益只有 1.16–1.35 倍**，不是 N 倍。
   不是实现错：这台机器的 decode 每次前向耗时随批大小近似线性上涨、
   prefill 吞吐完全不涨，能省的只有"每次调用的固定成本 + 少 prefill 几次"那一段。
2. **N=4：1.15–1.2 倍**（两轮 1.16x / 1.19x 均值，1.14x / 1.22x 最小）。
3. **测到的最大批 8 仍然划算**（1.32x / 1.35x 均值），但每次翻倍收益递减
   （1.11 → 1.19 → 1.35），且 8 条时解码单步已 41–50 ms——再往上加只会更平。
   脚本受"8 份任务"限制，**没有测到从哪一档开始不划算**。
4. **前缀共享比批处理本身更值得做**：省 41%（相对顺序 2.11x）。
   生产上若能把同一份文件上下文的 KV 跨批次常驻，收益比这里的每轮 0.81 s 更大。
5. 机器不空闲：第一轮 loadavg 4.3→20.3（N=8 明显被抢占，同档 max/min 差到 1.7 倍），
   第二轮 6.2–10.7。所有数字都给 min 与均值，判断以第二轮为准。
6. 正确性上两种模式**没有差别**：93/93 逐字一致。8 份任务里小模型自己只做对 6 份
   （`in_stock_books` 回了真实字段名 `isbn` 而不是候选 id；`verified_reviews` 多返回一个字段），
   两种模式错在同一处——这是模型决策准确率（本节固定任务集 75%），不是批处理引入的。

### 这次没有验证的

- **批大小 > 8 没测**（脚本上限是 8 份任务）。"从哪一档开始不划算"没有实测点，
  只有"单步耗时随 N 线性上涨"的趋势外推。
- **长输出没测**：决策只有 26–32 token（`max_tokens=64`）。写整个函数正文（512+ token）时
  解码占比高得多，批处理的账要重算。
- **提示长度只有 193–215 token**（共享前缀那条 799）。没有测"长提示 × 大批量"的组合。
- **只有温度 0（argmax）**；采样、温度 >0 的批量路径没测。
- 口径差异（如实披露）：顺序数字是**生产路径**（`MLXEngine.generate` → mlx_lm `generate_step`，
  算全部位置的 logits）；批量数字是**原型**（输出头只算末位 logits，复用常驻 tokenizer）。
  所以 1.16–1.35x 是"原型 vs 生产"，不是同一份代码换个调度。
- **批量路径没有流式返回**：N 条答案在同一次前向结束后一起出来。若调用方关心的是
  "第一条答案多快"而不是总吞吐，顺序路径先给结果（0.45 s 一条 vs 1.6 s 四条）。
- **KV 跨批次复用没测**：每次批处理都重新 prefill；本节只回答了"同一次调用内共享前缀"。
- 内存数字是 MLX 自报峰值 + 本进程 RSS，不是整机占用，不含其他进程。
- 合成提示的 mask 对照（37/53/71 token）只做了一轮 10 token 的逐 token 比对，不是多轮统计。

## 排序槽位的四项实测，以及它顺手暴露的一次生产回归（2026-09-20）

[选择路线的槽位](12-selection-slots.md)规定：每加一个槽位必须量四件事。
排序槽位早已并入 `chooseonly/decide.py`（`sort_field` / `sort_desc`，由调用方通过
`sort_enabled` 显式开启），但这份数字一直没记档。补测的过程分成三段：先发现脚本
自己有两处缺陷，再发现**生产主路径被这次改动弄坏了**，最后才拿到四项数字。

### A. 脚本缺陷一：排序任务被结构性地锁死为失败

`bench/sort_slot.py` 的 `select_once()` 调 `build_decision_prompt()` 和
`parse_decision()` 时**都没有传 `sort_enabled`**（全文件一次都没传）。而宿主在未启用时
会在系统提示和用户消息里都写明"严禁输出 s 或 d"，`parse_decision` 也会拒绝任何 s/d。
于是：模型照规矩不排序 → `check_body` 判失败；模型不守规矩回 s/d → 解析就被拒。
**无论模型怎么做都不可能通过**，与模型能力无关。已修（按任务类型显式传 `sort_enabled`）。

顺带修掉同一处的一个口径错误：旧提示基线原来只替换系统提示，但加槽位时
**用户消息也新增了一行** `排序槽位：…`，所以两边的差被低估。现在两边一起去掉那一行。

### B. 脚本缺陷二：拒绝质量那 8 条是假通过

`refusal_report()` 同样没有传 `sort_enabled=True`，于是 8 条带 s/d 的坏决策全部先被
"排序槽位未启用"这道理拦住，**一条都没走到真正的排序校验器**。
修之前打印的 8 个 ✓ 全绿——但把排序校验器整个删掉，它还是全绿。
修之后每条报的是各自真实的原因：

```text
✓ 排序字段候选表里没有: 未知的排序字段 id：'f9'（s 只能选字段候选：f0, f1, f2）
✓ 拿条件 id 当排序字段: 未知的排序字段 id：'c0'
✓ 自造字段名当排序字段: 未知的排序字段 id：'name'
✓ 排序字段不在返回字段里: 排序字段 'f2' 不在返回字段 r 里……
✓ 只给排序字段没给方向: 决策给了排序字段 s 却没给方向 d
✓ 只给方向没给排序字段: 决策给了排序方向 d 却没给排序字段 s
✓ 方向不是 asc/desc: 未知的排序方向：'横向'
✓ 旧长键想夹带排序: 决策混用了两套键
```

### C. 真问题：这次改动把主路径弄坏了

脚本修好后第一次跑出结果，**不排序的老任务全部失败**：

| 任务 | 旧提示（加槽位前） | 新提示（当时的生产提示） |
| --- | --- | --- |
| orders 对照：其他不变 | 3/3 | **0/3** |
| users 对照：保持原顺序 | 3/3 | **0/3** |
| products 对照：其他不变 | 3/3 | **0/3** |
| priced 对照：其他不变 | 3/3 | 3/3 |
| 老任务 A：过滤 + 裁字段 | 3/3 | **0/3** |

生产 CLI 上一次 `--dry-run` 就复现了：

```text
function=fn0，不过滤，return_fields=f1=id、f2=name，排序=不动原文
--- a/users.py
+++ b/users.py
-        if user["active"]:
-            result.append({"id": user["id"], "name": user["name"]})
+        result.append({"id": user["id"], "name": user["name"]})
```

模型回的是 `{"r": ["f1", "f2"]}`——**整个 `f` 键被省掉了**。
而 `parse_decision` 把"键缺失"按"不过滤"处理（既有的、有意的设计），
于是这次失败**不会被拒绝，只会被静默执行**：过滤条件那行代码被删掉，
产物仍是合法可跑的 Python，只看 diff 很像"一个干净的改动"。
这正是上文"实测中发现并修掉的缺陷"第 4 条那类失败，只是这次它藏在宿主的默认值里。

### D. 定位：不是排序条款，是那行示例被删了

把变量拆开逐项对照（同一批 5 条不排序任务，温度 0，各一次）：

| 配置 | 通过 |
| --- | --- |
| A 旧系统提示（含 `正确形状示例` 行） | **5/5** |
| B 旧系统提示 + 用户消息里那行"排序槽位：未启用……" | **5/5** |
| C 旧系统提示 + 系统提示里追加"未启用时严禁输出 s 或 d" | **5/5** |
| D 现状：删掉示例、换成上述禁令 | **1/5** |

用户消息那行禁令无害（B），系统提示里的排序条款也无害（C）；
**唯一原因是系统提示里那行 `正确形状示例` 被删掉了**（D）。删掉之后模型回
`{"r": ["f1","f2"]}`，条件候选一个都不选。

这与上文早就量过的一次诊断方向一致（"把系统提示里那行示例删掉……1.5B 也变差了"）。
当时只当作诊断附注，没有把它当成生产提示的硬约束；这次它变成了真实回归。


### E. 修法与验证

`chooseonly/decide.py` 的 `DECISION_SYSTEM_PROMPT` 恢复成加槽位前的逐字原文（含那行示例），
排序条款只在启用时才追加：

```text
sort_enabled=False → 系统提示 = 基础原文（含示例）；禁令只留在用户消息的 sort_note 里
sort_enabled=True  → 系统提示 = 基础原文 + 启用条款
```

安全边界没有因此变松：**真正的强制在宿主**——`parse_decision(sort_enabled=False)`
收到 s/d 直接拒绝（下面第 4 项就是它）。提示词措辞从来不是那道闸。
`tests/test_decide.py` 里原先有两条断言反过来"锁死"了无示例设计
（`assert "{" not in system`），已经按实测结论改成"基础示例必须在、排序示例一个都不给"。

生产 CLI 复验（同一条指令、同一个文件）：

```text
function=fn0，filter=c0=active，return_fields=f1=id、f2=name，排序=不动原文
（无差异）
```

### F. 四项数字（修复后；M1 Pro 16GB，load average 6.6 → 9.3）

1. **正确率：排序任务 18/18**（6 类任务 × 3 次）。判断走运行时行为：`exec` 组装出的
   函数后真调用，比对过滤结果、返回字段**和顺序**，另核对函数外的字节逐字未动、
   该出现的排序行确实出现、原文旧排序确实消失。**修复前同一脚本只有 3/18。**
2. **输出 token 的税**

   | 决策类型 | 旧提示 | 新提示 | 差 |
   | --- | --- | --- | --- |
   | 不用排序槽位（5 条） | 28 | 28 | **+0** |
   | 用上排序槽位（4 条配对） | 28 | 43 | **+15** |

   不用槽位的决策一分钱不涨——因为启用条款只在 `sort_enabled=True` 时才进提示。
   输入侧每条约多 20 个 prefill token（≈0.02 s），不计入这里的输出税。

   **另外单独量过"修法本身的代价"**（第三种口径，别和上面两行混）：把示例行加回系统提示
   （无示例 → 有示例），同一条不排序指令的输出从 **20 → 28 tokens（+8）**。
   这是"过滤条件不再被丢掉"的价钱，属于一次性付给所有决策；上面那张表量的是
   "加槽位"的价钱，两回事。
3. **老任务回归：15/15**（4 条"其他不变 / 保持原顺序"对照 + 老任务 A，各 3/3）。
4. **拒绝质量：8/8**，每条都是各自真实的原因（见 B 节列表）。

耗时：排序任务单次生成 0.58–0.70 s（43 tokens），不排序 0.42–0.50 s（28 tokens）；
模型加载 0.64 s。机器当时有其他负载，只给区间，不跨运行比较。

### G. 这次实测改掉的两条旧结论

- [选择路线的槽位](12-selection-slots.md)原来写"每加一个槽位，**每一次**决策的输出都会变长
  几个 token"。**实测不成立**：只要启用条款只在启用时进提示，不排序的决策是 +0。
  真正的税只落在用得起它的决策上（+15 tokens）。
- 上文任务 B 记录的"选择路线 5/5"，**在加排序槽位之后一度失效**（老任务 A 从 3/3 掉到 0/3）。
  加槽位到修复之间那段代码不应再作为 5/5 的依据；本文 F 节是修复后的复验数字。

### H. 一条可以推广的教训

`f` 键缺失被当成"不过滤"是合理设计，但它让"模型没有选条件"变成**不会报错的失败**：
宿主无从区分"模型确实要求不过滤"和"模型忘了给条件"。
凡是有默认值的决策字段，都要在回归里专门盯——这也是为什么这次必须有一条
"同一份源码、同一条指令、只差排序"的配对照组，而不是只看排序任务过没过。

### I. 修复后仍然存在的限制（如实记录，不是本次引入的）

在**带复合条件**的函数上（`if order.paid and not order.shipped:`），1.5B 会**多选一个返回字段**：

```text
指令：只保留 paid 为真的项，返回 order_id 和 total，其他不变
决策：filter=c0=paid ✅   return_fields=shipped、order_id、total ❌（多选了 shipped）
diff：- if order.paid and not order.shipped:
      + if order.paid:
      -     rows.append({"order_id": ..., "total": ...})
      +     rows.append({"shipped": ..., "order_id": ..., "total": ...})
```

这与上文那个"多选了一个字段"的失败模式是同一个。对照验证过：
**旧提示（加槽位前）和修复后的提示在这个函数上给出逐字相同的结果**
（`r=['shipped','order_id','total']`，`f=c0`），所以它是既有的模型能力限制，
不是这次提示修复引入的。

两点区别要说清楚：

- 它**不是静默失败**：多出来的键就写在那行改动的 diff 里，确认门会把它展示出来；
  而"丢掉 `f` 键"那类失败看上去像一次干净的清理，更容易被放过。
- 复合条件本身另有已知边界：选择路线一次只保留一个条件，
  程序会附提示交大模型判断（上文"已知边界"里那条），不会自己改用别的路线。

**所以修复达到的效果是"从静默错变成可见的、可判断的结果"，不是"准确率变成 100%"。**
这个函数上的字段选择仍需要更强的执行器或专用打分器，属于 `docs/10-tomorrow-goal.md`
里已经给出的下一步选择，不在本轮范围内。

## Mercury 2.5（扩散 LLM）实测：选择路线不行，生成路线很行（2026-09-20）

Mercury 是 Inception Labs 的扩散语言模型。**它没有开源权重**：
HuggingFace 上 `inceptionai` 与 `inception-labs` 名下零模型，官方文档只有 API 用法，
没有任何 weights/download/license 字样。所以本机跑不了，只能走 API。

好消息是它是 **OpenAI-compatible**，`chooseonly/api_engine.py` 零改动就接上了。

### 必须的配置：`reasoning_effort: "none"`

实测不设或设 `low`/默认时，一个"回复 OK"的请求会烧掉 **207–210 个推理 token**；
配上小的 `max_tokens` 时 `content` 直接是 `None`（第一次跑出 0/5 就是这个原因，
不是模型答错）。设成 `none` 后推理 token 归零，内容正常。

另外连续快速请求会触发 **HTTP 400 限流**，需要退避重试。

### 选择路线（输出 1–2 个 token）：慢，不该用

同一候选页、同一 5 条 CodeTask，`reasoning_effort=none`：

| 执行器 | 准确率 | 延迟 |
| --- | --- | --- |
| 本地 Qwen1.5B | 2/5 | 0.33–0.60 s |
| DeepSeek Flash | **5/5** | 0.37–2.10 s |
| **Mercury 2.5** | **5/5** | **5.68 s** |

直连（不走代理）也是 ~4.8 s，所以延迟在服务端往返，不是代理造成的。
**原因很清楚：扩散的加速来自"一次前向并行出多个 token"，输出只有 1 个 token 时没有东西可并行。**

### 生成路线（长输出）：**跑不过 DeepSeek Flash**（本节已修正）

最初只用一条"按输出长度扫描"的样本（1116 token / 4.56 s = 244.9 tok/s）得出了
"长输出上 Mercury 快 3–4 倍"的结论。**那是对着本地模型比的结果，没有和 API 对手比，
结论不成立。** 补做三方对照后（同一个"写整个模块"任务，各 5 次，判断用真的 import
并调用三个函数）：

| 后端 | 通过 | 输出 tok | 平均墙钟 | tok/s |
| --- | --- | --- | --- | --- |
| 本地 Qwen2.5-Coder-1.5B-4bit | **0/5** | 280 | 6.86 s | 41 |
| **DeepSeek Flash（deepseek-v4-flash）** | **5/5** | 397 | **2.96 s** | **134** |
| Mercury 2.5（扩散） | 4/5 | 248 | 5.86 s | 42 |

本地模型的失败是语义的：`filter_active` 返回了 `['active','id','name']`，5 次都多带
`active` 字段。

再补一个更长的 CLI 任务（各 5 次）：

```text
Mercury          中位 2303 tok ｜ 8.07 s ｜ 252 tok/s ｜ 7.71–8.91 s
DeepSeek Flash   中位 3868 tok ｜ 11.73 s ｜ 321 tok/s ｜ 11.54–13.70 s
```

**DeepSeek Flash 每 token 更快（321 vs 252）也更稳。** 它墙钟更长只是因为它写了
约 1.7 倍的量。所以生成路线**没有出现 Mercury 的生态位**。

边界：这不是"扩散 vs 自回归"的架构判决。两者跑在不同厂商、不同机房、不同网络路径上，
且 Mercury 单次延迟方差很大（实测出现过 2.75 s 到 7.60 s）。能说的只是：在这两条具体
路线、这两个具体入口上，DeepSeek Flash 每一项都更好。

### 输出格式：纯机械问题，一条规则即可，不需要大模型

Mercury 有 **5/8 次在输出末尾多吐一个孤立的 ` ``` `**（只有关闭标记、没有开头）。
这看起来像 3/8 的通过率，但逐条分类后是：

```text
8 次试验：原始通过 3/8；只加一条"剥掉首尾围栏行"的规则后 8/8
纯机械失败 5 次｜语义失败 0 次
```

**语义失败是零。** 所以这类问题不该花一次大模型往返去修——`strip_code_fence`
