# 下一步实验顺序（2026-09-20 记录）

## 适用范围先说清楚

本项目的最终形态收敛为：

```text
只做 Python 一个目标语言
只做一种指令语言
只做函数级及以下的改动
小模型用组合/选择/填空的方式产出，不自由发挥
大模型负责规划、拆解、检查、修正
```

所以后面所有实验都只在这条线上做，不扩多语言、不扩多范式。

## 一条必须记住的张力：窄化 ≠ 拆细

用户提出的这条约束要写进决策：

> 拆得太细，成本可能就提上去了。

因为每次拆分都是**一次完整往返**。我们实测过：本机一次调用地板约 0.33 秒、
一次选择约 0.6–1.4 秒、一次 API 选择 0.4–2.1 秒。拆成 N 段就是 N 次往返。

所以有两种"变窄"，代价完全不同：

| 做法 | 例子 | 代价 |
| --- | --- | --- |
| **免费变窄**：同一句指令，只要求产出更小的片段 | "只输出函数体，不要 def 行" | **不增加往返**，还减少输出 token（更快） |
| **收费变窄**：把一件事拆成多件事分别调用 | "先写第 1 个函数，再写第 2 个" | **每拆一次多一次往返** |

**优先做免费变窄。** 它同时改善正确率和速度；收费变窄只在"不拆就做不对"时才用。

## 实验顺序（按代价排）

### 第 0 步（已完成，纯赚）
**前缀 KV 复用接进生产**。实测长上下文省 41.5%、短上下文省 10.4%，输出逐字节相同，
与模型架构无关，无风险。

注意：这条**不能照搬到扩散**。BiCache（arXiv 2606.07571）实测把自回归的前缀 KV 复用
直接用于扩散会让精度崩到接近 0；正解是只重算约 20% 的 anchor token（ACache）。

### 第 1 步（**已做，结论是负的**）免费变窄：填空式生成

同一个模型、同一批真实任务，只改"要求产出什么"，调用次数都保持 1 次：

```text
A 现状：  写完整的函数            ← 输出整个函数
B 只填函数体：给出 def 行，只输出 body
C 只改片段：只输出要替换的那一小块
```

**实测结果：变窄没有提高通过率，反而全错。**

| 协议 | 简单形状 | 真实形状 | 输出 tok |
| --- | --- | --- | --- |
| A 整函数 | **5/5** | 0/5 | 72 / 93 |
| B 只填函数体 | 0/5 | 0/5 | 71 / 96 |
| C 只改片段 | 0/5 | 0/5 | 38 / 38 |

逐条诊断（共试了 5 种变体，含带示范的改进版）：

| 变体 | 失败方式 |
| --- | --- |
| B 只填函数体 | 无视协议，照样输出整个文件（含 def 行）→ 组装后重复 |
| C 只改片段 | 照做了协议，但 dict 里仍留着 `active`（该去掉） |
| B2 带示范 | 首行漏缩进，且 dict 仍错 |
| C2 只改字典 | 语法错误 |
| B3 修好缩进 | **整个丢了 `result = []` 初始化** → `NameError` |

**结论：这个模型在改变输出形状后会丢必要部分。** 同一句指令、同一个模型，
维持原有形状（整函数）时 5/5，一旦只要求片段就漏初始化、留错字段。

这与公开结论一致：**FIM 的收益来自"训练过这个格式"，不是"提示出这个格式"**
（CodeGemma、StarCoder 等都是在训练阶段就带 FIM 目标）。

**所以"免费变窄"并不免费——它需要一次微调。** 这一步从"当天可做"改为
"需要训练投入"，优先级据此下调；在决定投入训练前，先做第 2 步（线性架构）。

### 第 2 步（**已做，结论是负的**）线性架构的第一次实测

`mlx-lm` 里已有实现可直接加载：`rwkv7.py`、`mamba2.py`、`falcon_h1.py`、`lfm2.py` 等。
实测对象：`LFM2-350M-4bit`、`Falcon-H1-0.5B-Instruct-4bit`、`RWKV-7-1.5B`（个人 6bit MLX 转换）。

同一台机器、同一条指令、同一判据（运行时真的调用函数）：

| 模型 | 参数 | 通过 | tok/s | 长上下文峰值内存 |
| --- | --- | --- | --- | --- |
| Qwen2.5-Coder-1.5B（自回归基线） | 1.5B | **3/3** | 56 | 1.20 GB @215 tok → 1.78 GB @1295 tok |
| LFM2-350M（混合） | 0.35B | 0/3 | **189** | 0.36 GB @264 → 1.13 GB @1569 |
| Falcon-H1-0.5B（混合） | 0.5B | 0/3 | 79 | 0.86 GB @355 → 2.05 GB @1915 |
| RWKV-7-1.5B（纯线性） | 1.5B | 0/3 | **44** | 1.72 GB @302 → 2.42 GB @4579 |

三条反直觉的实测：

1. **RWKV-7 比自回归还慢**（44 vs 56 tok/s）。线性架构理论上每 token 常数开销，
   但这条实现没优化，或 6bit 量化开销吃掉了收益。
2. **"混合"架构内存并不恒定**：LFM2 单位 token 的内存增长甚至快于 Qwen，因为它仍带注意力层。
3. **纯线性也不是常数**：RWKV-7 的增长比 Qwen 的 KV 慢约 3.4 倍（0.16 vs 0.54 MB/token），
   但绝非恒定——部分原因是单次前向必须把整段输入放进内存，峰值含输入本身；
   要真正体现常数状态需把长上下文分块流式处理。

质量上也做不出来：RWKV-7 把输入原样吐回并附带对话垃圾；Falcon-H1 在代码里写了中文全角冒号。

边界：RWKV 那个是**个人测试转换**而非官方权重；LFM2/Falcon-H1 比 Qwen 小 3–4 倍，
失败有尺寸因素；**唯一同尺寸对照是 RWKV-7-1.5B vs Qwen-1.5B，结果是线性更慢且做不出任务**。
这也是首批公开数据：RWKV-7 论文全文没有任何 HumanEval/MBPP 数字。

### 第 3 步（需要服务器）扩散 vs 自回归的交叉点复现
这是判定"扩散能否用于生成"的唯一严谨实验：

```text
同一张卡、同族权重：
  Fast-dLLM v2 1.5B   vs   Qwen2.5-1.5B-Instruct
扫步数 {512, 256, 128, 64, 32}，画 pass@1 – 秒/题 曲线
与 arXiv 2509.11252 在 A100 上的交叉点（~64 步 / ~32 步）对照
```

已有的系统结论（8×A100-40GB）：扩散要 ~64 步追平"无 KV 的自回归"、
~32 步追平"带 KV 的自回归"，而步数掉到 32 时质量从 61.6% 掉到 38.4%。

`Fast-dLLM v2 1.5B` 是目前唯一"小而本地、非自回归、且在同族 1.5B 上验证过"的候选
（在 Qwen2.5-Instruct 上做块扩散，约 1B token 微调）。障碍是推理栈走 CUDA。

需要 ≥24GB，A100/H100 最好。

### 第 4 步（可选）极小模型与"窄度"的关系
官方数据给出一条硬边界：`Qwen2.5-Coder-0.5B` 的 HumanEval 有 61.6%，
但 BCB-Hard 只有 1.4、LiveCodeBench 2.0、Aider 真实编辑 14.3%——**不可用**。
1.5B 是 6.8 / 6.1 / 31.6%，边缘；3B 起才像样。

但反例是 `phi-1-small`（350M，HumanEval 45%）：它靠的是**任务极窄**（只做 Python 函数级），
不是架构更强。这与我们全部实测一致：窄任务 5/5、宽任务 0/5。

**结论：让极小模型可用的关键是窄度，不是尺寸。** 所以第 1 步优先于第 4 步。

## 不要做的事

- 不扩多语言、不扩多目标语言
- 不为扩散改架构；`Engine` 协议只有一个方法，后端可换，先留位置
- 不做自动失败训练、自动修复闭环、CoT
- 不在没有实测优势前更换生成后端
